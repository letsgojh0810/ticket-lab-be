## 🎯 프로젝트 개요

수만 명이 동시에 접속하는 티켓 예매 시스템에서 정해진 좌석만 정확히 판매하고 빠른 응답 속도를 유지하며 안정적으로 서비스하는 것을 목표했다.

해당 프로젝트는 도메인 특성을 고려하여 가장 중요한 목표를 다음 3가지로 정했다.

1. 데이터 정합성(+트랜잭션 일관성)
2. 멱등성 보장
3. 동시성 제어

### 핵심 과제

| 문제 | 해결 방법                    | 성과 |
|------|--------------------------|------|
| **동시성 이슈** | Redisson 분산 락 + Redis 캐싱 | 중복 예매 방지 |
| **DB 과부하** | 락 → 캐시 → DB| DB 부하 감소 |
| **트래픽 제어** | Redis ZSet 활용| Active User 100명 제한 |
| **응답 속도** | Kafka 비동기 이벤트 처리 Kafka| 응답시간 향상 및 결합도 제거 |

## 📨 이벤트 기반 아키텍처

### 문제: 동기 처리의 한계

```java
public String reserve() {
    // ... 예매 로직 ...
    emailService.sendConfirmation();
    smsService.sendNotification();
    statisticsService.update();
    return "SUCCESS";
}
```

**문제점:**
- 외부API(SMTP, 카카오톡 등) 서버 장애 시 예매도 실패

### 해결: Kafka 이벤트 기반

```java
// ✅ After: 비동기 이벤트 발행
public String reserve() {
    // ... 예매 로직 ...
    kafkaProducer.publish(event); // 밀리초 단위
    return "SUCCESS"; // 즉시 응답!
}

// 별도 Consumer에서 비동기 처리
@KafkaListener(topics = "reservation-events")
public void consume(ReservationEvent event) {
    emailService.send();    // 비동기
    smsService.send();       // 비동기
    statisticsService.update(); // 비동기
}
```

### Kafka 설정

**Producer:**
- `acks=all` - 모든 복제본 확인 (신뢰성 최우선)
- 재시도 3회
- Key: seatId (같은 좌석 이벤트 순서 보장)

**Consumer:**
- 수동 커밋 (At-least-once 보장)
- 처리 실패 시 자동 재시도
- Consumer Group: `ticket-reservation-group`

* **동시성 제어**: 1,000명의 유저가 한정된 100개의 좌석을 두고 경쟁하는 상황 시뮬레이션

### 4. 트러블슈팅: 1차 테스트 실패

#### 문제 발생

1차 테스트 결과, 예상했던 성공 100건에 못 미치는 **79건**에서 멈추는 현상이 발생했다. 또한 모든 유저가 Active 큐에 진입하지 못하고 고작 270명만 진입하는 문제가 발생했다.

<p align="center">
<img src="static/img/test7.png" width="600" alt="실패 결과">
</p>

> **원인 분석**
> * **스케줄러**: Score 상위 유저부터 Active로 전환 (userId 7, 55, 45...)
> * **테스트 코드**: userId 1번부터 순차적으로 요청을 보냄
> * **결과**: 아직 Active 권한을 얻지 못한 유저들이 요청을 보내면서 403 Forbidden 에러 발생. 결과적으로 270명만 정상 진입함.
>  .
> 

#### ✅ 해결 방법

각 유저가 자신의 상태가 **Active**가 될 때까지 대기한 후, Active 권한을 획득했을 때 예매을 시도하도록 테스트 코드를 수정했다. 즉, 모든 유저가 대기 후 모두 Active 큐에 들어갈 수 있게 설정했다.

### 7. 트러블슈팅: 좌석 1만 개 + 결제까지 붙여서 다시 테스트하다 만난 문제들

3월에 좌석 상태의 기준을 Redis에서 DB로 바꾼 뒤(`eed0f66`) 처음으로 규모를 키워서 다시 돌려 봤다. 좌석은 1만 개로 늘렸고, 결제는 모의 PG(성공 80% / 실패 20%)를 따로 띄워 연결했다. 우선 유저 2~3천 명으로 검증한 뒤, 마지막으로 **1만 석 / 2만 명**까지 돌려서 전량 매진되는 것을 확인했다. (아래 7번의 결과 표 참고, 재현 방법은 `load-test/README.md`)

#### 1. 같은 좌석이 두 번 팔렸다 (중복 예약)

1,000명이 100석에 몰리게 했더니 예약이 100건이 아니라 103~110건이 생겼다. 같은 좌석에 예약이 2건 붙은 좌석이 3~9개였고, 네 번 돌려서 네 번 다 나왔다.

> **왜 그랬나**
> `spring.jpa.open-in-view`는 기본값이 켜져 있어서, 한 요청이 끝날 때까지 읽어 온 엔티티를 JPA가 계속 들고 있는다.
> 우리 코드는 락을 잡기 *전*에 좌석을 한 번 읽고(존재 확인), 락을 잡은 *뒤*에 "DB에서 최신 상태 재확인"을 한다. 그런데 이 두 번째 조회가 실제로는 DB까지 가지 않고, 처음 읽어 둔 `AVAILABLE` 객체를 그대로 돌려줬다.
> 그래서 앞 사람이 이미 `SELECTED`로 바꿔서 커밋했는데도, 뒤에 온 사람 눈에는 여전히 `AVAILABLE`이었다.
> 1월 코드는 락 안에서 Redis 캐시로 판정해서 이 문제가 없었다. 3월에 "DB를 원천으로" 바꾸면서 드러났다.

**✅ 해결**: `spring.jpa.open-in-view=false` 한 줄.

**확인**: 꺼 놓고 같은 테스트를 3번 돌렸더니 3번 모두 정확히 100건, 중복 0.

#### 2. 대기열이 멈췄다 (조회할 때마다 줄 맨 뒤로 밀림)

유저 2,000명 / 활성 500명으로 돌렸더니 500건까지 처리하고 그대로 멈췄다. 그때 활성 상태인 500명을 열어 보니 전부 **상태를 조회하지 않고 있는 유저**였다. (1차 테스트에서 겪은 "승격 순서와 테스트 순서가 다르다"와 같은 증상)

> **왜 그랬나**
> `status`를 조회하면 `registerAndGetRank()`가 호출되는데, 이 메서드가 `ZADD`로 점수(진입 시각)를 **지금 시각으로 덮어쓴다.**
> 실제로 대기 500번째 유저가 `status`를 딱 한 번 조회했더니 999번째로 밀렸다.
> 즉 새로고침을 열심히 하는 사람일수록 승격이 안 되고, 가만히 있는 사람이 먼저 입장한다.

**✅ 해결**: 이미 줄에 서 있으면 점수를 건드리지 않도록 `ZADD NX`(`addIfAbsent`)로 바꿨다.

**확인**: 활성 500명이 가득 찬 상태에서 한 유저가 5번 조회해도 점수와 순번이 그대로였고, 자리가 하나 나자 가장 먼저 줄 선 유저가 입장했다.

---

#### 3. 활성 유저 수를 셀 때마다 Redis 전체를 훑고 있었다

`status`를 부를 때마다 활성 유저 수를 `SCAN`으로 센다. SCAN은 활성 키만이 아니라 **Redis 안의 모든 키(좌석 캐시 1만 개 포함)** 를 돌고, 도는 도중에 키가 바뀌면 중복해서 세거나 값이 틀어질 수 있다. 폴링이 몰리면 가장 먼저 부담이 될 곳으로 보인다. (실제 영향 크기는 측정하지 못했다)

**✅ 해결**: 활성 유저를 "만료 시각을 점수로 가진 ZSET"(`ticket:active:expiry`)에도 같이 기록하고 `ZCOUNT`로 센다. 스케줄러가 돌 때마다 만료된 항목은 정리한다.

**확인**: 상태 응답의 활성 유저 수가 정확히 500으로 나왔고, 테스트가 끝나면 0이 됐다.

---

#### 4. 성공 지표가 계속 0이었다

Grafana에서 `reservation_success`, `payment_success`, `payment_failed`가 움직이지 않았다. 카운터는 등록만 되어 있고 **값을 올리는 코드가 없었다.** (언제부터 그랬는지는 확인하지 못했다)

**✅ 해결**: 좌석 선점에 성공하면 `reservation_success`를, 결제 콜백이 DB에 커밋된 뒤(`AFTER_COMMIT`) `payment_success` / `payment_failed`를 올린다.

**확인**: 2,000명 테스트에서 예약 성공 2,000 / 결제 성공 1,600 / 결제 실패 400이 그대로 찍혔다.

---

#### 5. 이탈한 사람의 좌석이 영영 안 풀렸다

결제를 안 하고 나가거나 결제 요청이 실패하면, 좌석은 `SELECTED`, 예약은 `HELD`로 계속 남고 그 유저의 활성 슬롯도 5분 동안 묶였다. 위 "6. 테스트 후기"에서 확인했다던 "이탈 시 좌석 자동 해제"는 DB를 기준으로 바꾼 뒤로는 성립하지 않았던 셈이다.

> **왜 그랬나**
> 5분 TTL은 Redis에 있는 좌석 캐시 키에만 걸려 있다. 지금 판단 기준은 DB인데, DB 상태에는 만료가 없다.
> 코드에서 `@Scheduled`도 `QueueScheduler` 하나뿐이었다.

**✅ 해결**: `HeldReservationExpirer`를 추가했다. 1초마다 TTL이 지난 `HELD` 예약을 찾아서 다음을 한꺼번에 처리한다.
- 예약은 `CANCELLED`, 좌석은 `AVAILABLE`로 되돌림
- Redis 캐시 삭제, 활성 슬롯 반납, SSE·Kafka 이벤트 발행

TTL은 `reservation.held-ttl-seconds`로 바꿀 수 있고 기본은 300초(5분)다.

**확인**: TTL을 5초로 줄인 별도 인스턴스에서 선점 후 9초 뒤 좌석 `AVAILABLE` / 예약 `CANCELLED` / 슬롯 반납을 확인했다. 기본 5분이 실제로 5분 뒤에 도는지는 기다려 보지 않았다.

**아직 남은 점**: 결제가 진행 중(`PENDING`)인 예약인지는 따로 보지 않고 만료시킨다. 결제 콜백이 TTL보다 늦게 오면 `confirm()`에서 예외가 날 수 있다.

---

#### 6. 결제 요청이 실패하면 슬롯이 5분 동안 묶인다 (테스트에서만 우회)

동시 결제 요청 중 일부가 500으로 실패했다. 모의 PG까지 도달한 건 87건뿐이었고, 나머지 113명은 `HELD`로 남았다. 이 113명이 활성 슬롯 200개 중 113개를 쥐고 있어서 대기열이 멈췄다.

> **왜 그랬나 (설계 쪽)**
> PG 호출이 실패하면 콜백이 오지 않는다. 그러면 예약과 슬롯을 정리해 줄 주체가 없다. PG 호출(`WebClient.block()`)에는 타임아웃도 없다.
>
> **이번 실패의 직접 원인 (추정)**
> 내가 띄운 모의 PG(파이썬 소켓 서버, 동시 연결 대기열이 5, HTTP/1.0)가 동시 연결을 못 받은 것으로 보인다. 앱 스택트레이스는 확인하지 못했고, 대기열 크기를 키운 뒤에는 다시 나오지 않았다.

**대응**: 테스트에서는 결제 요청이 실패하면 바로 세션을 반납하게 했다. 앱 쪽 PG 타임아웃과 실패 처리는 아직 손대지 않았다.

---

#### 7. 테스트 코드에서 배운 것들

- **서버가 승격하는 순서대로 유저를 돌려야 한다.** 승격된 유저를 아무도 안 챙기면 슬롯이 교착된다. (1차 테스트 실패와 같은 유형)
- **좌석 목록은 1초에 한 번만 받아서 공유한다.** 1만 건이라 한 번에 약 667KB(46ms)여서, 유저마다 매번 받으면 부하가 커진다.
- **결제에 실패한 유저는 줄을 다시 서서 재시도해야 한다.** 안 그러면 수요가 2,000명인데 확정이 1,600에서 멈춘다.
- **"다 팔렸나"를 보려면 유저가 좌석보다 많아야 한다.** 유저가 적으면 좌석이 남는 게 당연하다.

| 조건 | 결과 |
|---|---|
| 유저 2,000명 / 좌석 1만 개 (결제 실패자 재시도) | 2,000명 전원 확정. 결제 성공률 80.03%, 실패로 취소 499건, 중복 0 |
| 유저 3,000명 / 좌석 1,000개 | 1,000석 전량 확정. 선점 1,249건 → 결제 성공 1,000건(80.06%), 실패로 풀린 249석은 뒤 유저가 다시 가져감, 중복 0 |
| **유저 20,000명 / 좌석 1만 개** | **1만 석 전량 확정.** 결제 시도 12,499건 중 성공 10,000건(80.0%), 실패로 취소 2,499건(좌석은 뒤 유저가 다시 가져감), 확정 예약 보유 유저 10,000명, 중복 0, 종료 후 대기열·활성 0 |

**1만 석 / 2만 명 테스트 조건과 수치**
- 서버 1대, 활성 유저 상한 500, `loadtest` 프로필(Hikari 풀 50, SQL 로그 끔), 모의 PG(콜백 3초 지연, 성공 80% / 실패 20%), 이탈·TTL 만료 시나리오는 제외
- 소요: 대기열 진입 6초, 예매 흐름 192초 (유저 2만 명의 계정 가입·로그인 준비에 별도로 126초)
- 예약 선점 요청 23,726회의 응답 시간: p50 47ms / p95 647ms / p99 1,136ms / 최대 1,702ms
- 락 타임아웃 469건(약 2%)이 났지만 재시도되어 최종 결과에는 영향이 없었다. DB 커넥션 풀은 활성 최대 4개, 대기 0이라 풀은 병목이 아니었다.
- 확인하지 못한 것: 서버 2대 이상일 때의 동작, Redis 좌석 캐시와 DB의 일치 여부, Kafka 이벤트 소비 여부

#### 8. 아직 못 고친 것들

코드 리뷰에서 나온 것들이고, 일부는 직접 재현해 보지 못했다.

**🔐 보안**
- 결제 콜백이 인증·서명 없이 열려 있고 `transactionKey`는 사용자에게 응답으로 돌아간다. 사용자가 직접 SUCCESS 콜백을 보내서 결제 없이 확정할 수 있다.
- 예약·대기열 API가 `userId`를 요청값 그대로 믿는다. (남의 `userId`로 선점 가능)
- 금액을 검증하지 않고, `cardNo`를 평문으로 저장한다.

**🧱 정합성**
- 상태 전이 가드가 없다. `Reservation.cancel()`이 `CONFIRMED`도 취소하고 `Seat.release()`는 상태를 안 봐서, 늦게 온 실패 콜백이 결제가 끝난 좌석을 풀 수 있다.
- 콜백·취소·만료가 락이나 버전 없이 같은 행을 바꾼다.
- 락 점유 2초 안에 커밋이 끝나지 않으면 중복 선점이 가능하다. (재현하지 못함) `reservation(seat_id)`에 유니크 제약도 없다.

**⚙️ 성능·운영**
- PG 호출에 타임아웃이 없다.
- 인덱스가 없다. (`reservation(status, reserved_at)`, `payments.transaction_key` 등) 좌석 목록은 페이징·캐시도 없다.
- 서버가 2대가 되면 대기열 승격과 만료 스케줄러가 원자적이지 않아 중복 실행될 수 있다.

**AS-IS:**
```redis
SADD ticket:active:users 100 101 102
# TTL 설정 불가 → 메모리 누수
```

**TO-BE**
```redis
SET ticket:active:users:100 "1" EX 300
SET ticket:active:users:101 "1" EX 300
# 각 키마다 TTL 자동 적용
```

**효과:**
- 브라우저 종료 시 5분 후 자동 제거
- Scheduler 장애와 무관하게 동작
- Redis 기본 기능만 활용 (간단)

### 6. Reservation에 실패한 기록까지 같이 두는 게 맞을까? (리팩토링 후보)

지금은 예약이 `HELD → CONFIRMED | CANCELLED`로 흐른다. 결제 실패, 사용자 취소, TTL 만료가 전부 `CANCELLED` 행으로 남는다. 2,000명 테스트만 해도 확정 2,000건 옆에 취소가 499건 쌓였다.

**이게 왜 마음에 걸리나**
- 취소 행이 계속 쌓여서, 조회나 만료 스캔을 할 때마다 `status` 조건을 달아야 한다.
- 좌석당 살아 있는 예약은 하나여야 하는데, 취소 행 때문에 `seat_id`에 유니크 제약을 못 건다. 중복 방어가 락과 앱 로직에만 기대고 있다.
- 같은 유저가 취소하고 같은 좌석을 다시 잡으면 `findBySeatIdAndUserId`(Optional)가 행 2개를 만나 500이 날 수 있다. (코드 리뷰에서 나온 지적이고 재현은 안 해 봤다)
- 결제 실패 / 사용자 취소 / 만료가 한 값에 섞여서 왜 놓쳤는지 알 수 없다.
- `Seat.status`와 예약이 "누가 이 자리를 잡았나"라는 같은 사실을 두 군데에 적고 있어서 어긋날 수 있다.

**이렇게 바꿔 보면 어떨까**
- `reservation`에는 살아 있는 것만 둔다 (`HELD`, `CONFIRMED`). `seat_id`에는 UNIQUE를 건다.
- 끝난 건 `reservation_log`로 보낸다. (결제 실패 / 사용자 취소 / 만료 + 시각, 사유)
- 옮기는 건 한 트랜잭션으로 묶는다. (로그 INSERT + 예약 DELETE + 좌석 해제) 세 경로가 같은 코드를 쓰게 한다.
- `payments.reservation_id`가 지워진 행을 가리키게 되니, 좌석·유저를 같이 저장하거나 로그를 참조해야 한다.

**순서**: 먼저 지금 코드로 대규모 테스트의 기준값을 잡고, 고친 뒤에 같은 테스트로 비교해 본다.
